# Echo Relay chat

Echo Relay is a small real-time chat laboratory: an Express health endpoint and native RFC 6455 WebSocket relay, plus a React/Vite single-page client. Public hub messages are readable by the relay. Private-room message bodies are encrypted in the browser with the Web Crypto API before the relay receives them.

## Run locally

Use Node.js 20 or newer. In one terminal:

```powershell
cd server
npm install
npm run dev
```

The server loads settings from `server/.env` automatically through `dotenv`; no PowerShell environment-variable commands are needed. Copy `.env.example` to `.env` once and set a long, random `ADMIN_TOKEN` that only the administrator knows. The ignored `.env` file contains local-only settings and must never be committed or shared. The supplied local `.env` uses port `3004` to avoid conflicts with the usual `3001` port; change `PORT` there if needed. The WebSocket endpoint is `/ws`; `/health` returns a basic server status. `CLIENT_ORIGIN` accepts a comma-separated allowlist of origins. Admin authorization is checked by the server against the token; setting a client-side flag alone does not grant moderation access.

In another terminal:

```powershell
cd client
npm install
npm run dev
```

Vite prints the local browser URL. The client’s server-address field defaults to `ws://<current-host>:3004/ws`, matching the supplied local server configuration. You can override it at build time with `VITE_WS_URL`. For deployment, serve the app and server over HTTPS/WSS, configure network/origin policy appropriately, and provide the WebSocket URL in the client. Web Crypto requires a secure browser context (HTTPS, or localhost for local development).

## Deploy: Vercel frontend + Render WebSocket server

The Vite frontend can be hosted on Vercel, but the long-lived WebSocket server must run as a persistent web service (for example, Render); Vercel serverless functions are not a replacement for this `ws` server.

1. Push this project to a GitHub repository. Keep `server/.env` out of Git; it is ignored. Do not reuse its local example token for production.
2. On Render, create a Blueprint from the repository and use the included `render.yaml`. When prompted, set `ADMIN_TOKEN` to a new, long, random secret. Set `CLIENT_ORIGIN` to the Vercel production origin after the Vercel project is created, for example `https://your-echo-chat.vercel.app` (no trailing slash). Render supplies `PORT` automatically. The service health endpoint is `/health`.
3. On Vercel, import the same repository as a project and set **Root Directory** to `client`. Use the Vite framework preset, build command `npm run build`, and output directory `dist`.
4. In Vercel project settings, add the environment variable `VITE_WS_URL` with the Render WebSocket address, for example `wss://echo-chat-server.onrender.com/ws`. Set it for Production (and Preview if needed), then redeploy; Vite embeds this value at build time.
5. After Vercel assigns the production domain, add that exact origin to Render's `CLIENT_ORIGIN` environment variable and redeploy the Render service. This origin allowlist is checked for both HTTP CORS and browser WebSocket handshakes.
6. Open the Vercel URL and join the chat. Enter the Render `ADMIN_TOKEN` in **Administrator credentials** to access the global admin panel. Never put the admin token in Vercel variables prefixed with `VITE_`, client source, or `VITE_WS_URL`.

If using a custom domain or Vercel preview deployment, add each intended frontend origin as a comma-separated value in Render's `CLIENT_ORIGIN`, then redeploy. Private-room encryption requires HTTPS/WSS, which the Vercel and Render hosted domains provide.

## Chat and encryption

- Leave **Room ID** blank to join the public hub. Public message text is sent as plaintext.
- To join a private room, use the same room ID and passphrase as other members. The passphrase is never sent to the relay. Each browser derives an AES-GCM-256 key with PBKDF2/HMAC-SHA-256 (100,000 iterations; UTF-8 room ID as the salt). Each message uses a newly generated cryptographically random 12-byte IV. Ciphertext and IV are Base64-encoded for relay.
- The relay validates private-message envelopes and room routing, supplies `receivedAt`, and relays the opaque ciphertext. It does not retain chat history or room keys. Room IDs are routing labels, not access-control secrets: anyone with the room ID and passphrase can join/decrypt. Choose a strong, unique passphrase and share it through a trusted channel.
- UUID v4 IDs and sender `sentAt` timestamps are generated by the client. Server `receivedAt` timestamps are generated on relay.

## Administration and protocol

Enter the configured admin token in **Administrator credentials** when joining. Select **Remember token on this device** to store it in this browser's local storage; it remains there until you uncheck the option or clear the browser data. This is convenient on a private computer, but local storage is not encrypted, so do not enable it on a shared or untrusted device. The **Use nickname "admin"** shortcut fills in the nickname; the server still verifies the token before granting administrator privileges.

Verified administrators see a global panel above the chat. It lists every active named private room and the public hub, including connected-user counts, and every connected user with nickname, room membership, and administrator status. The panel refreshes as clients join or leave and has a manual **Refresh** action. An admin may ban users from any room from this panel; the server closes the target socket with WebSocket code `1008` (Policy Violation) and blocks that nickname from joining any room for the lifetime of the server process. A restart clears the in-memory ban list.

Global monitoring uses the `ADMIN_SUBSCRIBE`, `ADMIN_REFRESH`, and `ADMIN_SNAPSHOT` WebSocket events. The server authorizes subscription, refresh, and moderation using the administrator status it verified from `ADMIN_TOKEN` on `JOIN`; clients cannot gain access by setting a UI flag or sending an admin event. Global snapshots are sent only to verified administrator subscribers. Regular `WELCOME`, `USERS`, `USER_JOINED`, and `USER_LEFT` events remain scoped to the member's current room, and messages are not exposed through the global panel.

The client and server share matching typed event, `User`, `AdminSnapshot`, and `ChatMessage` contracts in their respective source trees. WebSocket frames are limited to 64 KiB, malformed events are rejected, binary frames are disallowed, and the server performs a ping/pong liveness check every 30 seconds.
